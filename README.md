# GroupFund

Android-приложение для ведения семейного/группового бюджета. Таблица с данными живёт в
**Google Таблицах** (штука на одного пользователя, signed-in аккаунт Google), а приложение
читает её, пересчитывает сводку и записывает обратно. Таблица — источник истины: «Сводка»
всегда вычисляется локально из листов `Участники` / `Платежи` / `Расходы` / `Настройки` /
`Сборы` и перезаписывается целиком.

| | |
|---|---|
| Пакет | `com.groupfund.app` |
| minSdk / targetSdk / compileSdk | 26 / 37 / 37 |
| Язык | Kotlin, Jetpack Compose (Material 3) |
| Сетевой слой | Retrofit + OkHttp + Gson поверх Google Sheets API v4 и Drive API v3 |
| Сборка | Gradle (Kotlin DSL, version catalog) |

## Возможности

- Вход через Google OAuth (play-services-auth), токен обновляется автоматически.
- Создание группы: приложение само создаёт таблицу (6 листов) и Drive-файл; доступ
  на чтение по ссылке выдаётся всем членам группы.
- Импорт существующей таблицы по ссылке (`https://docs.google.com/spreadsheets/d/<id>`)
  или штрих-коду (ZXing).
- Ежемесячные взносы: окно месяцев группы, вступление с произвольной даты,
  месяцы «без взноса», частичные оплаты.
- Сборы: общие (входят в бюджет) и отдельные (вне общего бюджета), взносы внутри сборов.
- Расходы с кругом участников; доля каждого округляется вверх до копейки — все платят
  одинаково, при неделимой сумме расход «подрастает» на несколько копеек.
- Автостилизация листа «Сводка» при каждой записи: поклеточные плитки месяцев,
  выделение текущего месяца, окраска баланса.
- Возвраты денег участникам, включая удалённых («ИСКЛЮЧЁННЫЕ»).
- Офлайн-пересчёт и повторное применение стилей; устойчивость к лимитам Google API (429).
- Экспорт сводки в PNG-картинку: кнопка «Поделиться» в экране группы
  (`data/export/SummaryImageRenderer.kt`).

## Структура таблицы

Листы (`Tabs.ALL`, `SheetLayout.kt`), создаются при создании таблицы:

| Лист | Колонки |
|---|---|
| **Сводка** | пересчитывается: заголовок, таблица по участникам и обязательным месяцам, «Итого», блок «РАСХОДЫ…», блок «ИСКЛЮЧЁННЫЕ…» |
| **Настройки** | код (например `"2026-09"`), сумма взноса, валюта, дата создания |
| **Участники** | Имя, Email, Дата вступления, Статус (`Активен`/`Удалён`), Дата удаления, Возврат, День рождения, Без взноса (`; `-список меток `2026-10`) |
| **Платежи** | Имя, Дата, Сумма, Комментарий |
| **Расходы** | Дата, Описание, Сумма, Участники (`; `-список, пусто = все), Доля на каждого |
| **Сборы** | Название, Дата, Цель, На кого, Взносы (`имя=сумма`, `;`), В общий бюджет (`ДА` / `—` ) |

Код месяца в DataFrame: `"2026-09"` (`MonthPlan.label()`). Числа в ячейках могут быть
любыми: Double, `"500"`, `"500,00"`, `"1 234,56 ₽"`, `"-300"` (`cellNum`).

## Бизнес-правила

Математика в `SummaryCalculator.kt`:

- **Окно месяцев** — N последних месяцев, `required = true` для каждого. Полная оплата
  месяца — внесённая сумма ≥ взноса месяца. Остаток перетекает на следующий месяц.
- **Внесено** (`totalPaid`) = сумма всех денежных поступлений участника минус строки
  `Возврат: …`. Теги не считаются деньгами «внутрь»:
  - `Сбор: X` — взнос внутри общего сбора `X`;
  - `Возврат из сбора: X` — излишек, возвращённый из общего сбора (учитывается как доход
    бюджета на будущие месяцы);
  - строки `Возврат: …` вычитаются из Внесено.
- **Сборы**: для общих сборов `collectionShare` считается честно `fairCollectionShares`
  (округление вверх по всем общим сборам разом). Отдельные сборы
  (`sharedWithBudget = false`) полностью изолированы: их взносы не входят ни в доход,
  ни в «Внесено», их доли не попадают в «Сборы»/«Расходы». Платеж `Сбор: <несуществующий>`
  трактуется как обычный доход.
- **Расходы**: `expenseShare` — `fairExpenseShares` по всем расходам разом; доля каждого
  округляется вверх до копейки (все платят одинаково).
- **Баланс** участника = Внесено − Доля расходов − Доля сборов.
- **Итоги**: внесено, сборы, расходы, баланс — по той же формуле. Если сумма не делится
  поровну, все платят по большей доле, поэтому итог может «подрасти» на несколько копеек
  (например, 2 сбора по 380 на 13 человек → каждому 58.48, итого 760.24).
- **ИСКЛЮЧЁННЫЕ**: удалённые участники; возврат = внесено − доля расходов.
- **`paidThrough` / «оплата до месяца»**: последний месяц, за который обязательная часть
  внесена полностью; `partiallyPaidMonth` — текущий частичный.

## Запись в таблицу

- `SheetsRepository.writeData()` — `values:batchClear` (диапазон A1:Z300 каждого листа)
  перед полной перезаписью через `batchUpdateValues`. Так не остаётся «хвостов» старых
  данных, которые порождали дубли и откаты.
- После записи применяются стили `SheetBeautifier` (плитки-заливки). Ошибки стилизации
  не валят запись данных — логируются как `Log.w("GroupFund", "applyStyle …")`.
- `deletePayment` не пересоздаёт строки: доли сборов пересчитываются из оставшихся
  строк `Σ "Сбор: X" + "Возврат из сбора: X"`.
- `parseCollections` дедуплицирует сборы с одинаковым именем: объединение участников,
  максимум взноса по каждому участнику, галочка «в общий бюджет» через ИЛИ.

## Лимиты Google API и ретраи

- Стандартные лимиты Sheets API: 60 запросов чтения и 60 записей на пользователя в минуту.
- `retryOnRateLimit` (в `SheetsRepository`) — экспоненциальный backoff 1с → 2с → 4с →
  … до ~60с (макс. 6 попыток), с джиттером. Это read-modify-write: при 429 операция
  перечитывает свежее состояние и дозаписывает — данные не теряются и не дублируются.
- `batchClear` добавляет один слот записи на операцию — учитывается при отладке.
- `retryOn429 = false` используется только для создания группы (операция идемпотентна).

## OAuth

`GoogleAuthManager` хранит токен через DataStore; при истечении обновляет через
`GoogleSignIn`/`play-services-auth`. Авторизация — `Bearer`-токен в каждый запрос.
При необходимости согласия выбрасывается `OAuthConsentRequiredException` с интентом.

## Бэклог

- **QR-сканер внутри приложения.** Сейчас ZXing используется только для генерации
  QR-приглашений (`UiUtils.kt`), а чтобы отсканировать чужой код и вступить в
  группу, нужно стороннее приложение. Нужен встроенный экран камеры
  (CameraX + ZXing `MultiFormatReader`) для сканирования приглашения и ссылки
  на таблицу.

## Известные баги

- **Скрытие недоступных групп не работает.** Группы, к которым у аккаунта нет
  доступа, всё ещё показываются в списке (`d1a18a5`, фильтр в `MainViewModel`).
- **Передача группы падает в 404.** Копирование таблицы (`copySpreadsheetToMe`)
  возвращает 404, несмотря на ретраи (`2447cf7`). Отложено до разбора.
- **Диапазоны.** После `912278e` (расширение диапазонов под рост таблицы) нужно
  проверить, что запись/чтение не обрезаются на больших группах.
- **Ложная отметка «не сдал» в расходах.** При раскрытии расхода часть
  участников помечается как не оплатившие долю, хотя такой пометки быть не должно.

## Сборка и тесты

```bash
# собрать debug-версию
./gradlew.bat :app:assembleDebug

# юнит-тесты (JUnit 4; папка app/src/test/...)
./gradlew.bat :app:testDebugUnitTest
```

Локальный `local.properties` должен содержать `sdk.dir`. Остальное — в `gradle/libs.versions.toml`.

Покрытие тестами (`app/src/test/java/com/groupfund/app/data/sheets/`):

- `FairSharesTest` — раскладка расходов и сборов с округлением вверх, все платят одинаково;
- `SummaryCalculatorTest` — месяцы, вступление, offMonths, частичные оплаты, сборы
  (общие/отдельные), возвраты, итоги, структура листа «Сводка», блок исключённых;
- `SheetsModelTest` — форматирование денег, разбор ячеек, round-trip листов
  Участники/Платежи/Расходы/Сборы/Настройки;
- `CollectionConsistencyTest` — консистентность сборов: частичные взносы, излишки,
  неконсолидированные строки, «Сбор: несуществующий», платёж постороннего.
